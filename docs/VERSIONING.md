# 个人定制版版本与构建规范

本规范于2026-10-25经维护者确认，后续构建、测试发布及生产提升必须遵循。它规定版本与来源追踪，不表示自动跟进上游，也不替代提交、推送和部署授权。

## 版本格式

展示版本统一为：

```text
v<官方基线>+pong.<YYYYMMDD>.<NN>
```

例如`v1.8.0+pong.20261025.01`。示例只说明格式，不代表该构建号已经分配或发布。

| 字段 | 规则 |
| --- | --- |
| 官方基线 | 当前实际采用的上游版本，可包含其原有预发布标识；记录对应上游提交，不根据远端最新标签自动修改 |
| pong | 本项目个人定制标识 |
| YYYYMMDD | 构建号分配时的北京时间日期；构建跨日仍保留已分配值，不使用部署日期 |
| NN | 当天从01递增的构建序号，超过99继续递增；同一项目开发、测试候选共用序号账本，不因环境各自从01开始 |

每次新构建先登记并占用编号，失败、取消、废弃后不复用；重试构建分配新号。版本一旦绑定构建产物不得指向不同内容。Git提交和文档修改不等于新构建，不必每次都增加构建号。

## Git、镜像与发布来源

Docker标签不支持`+`，使用可追溯映射：

```text
展示版本：v1.8.0+pong.20261025.01
镜像标签：beecount-cloud:1.8.0-pong.20261025.01-g<源码短哈希>
```

Docker标签中的`-pong`仅是存储标签映射，不作为SemVer版本字符串参与更新比较。

- 构建清单必须记录展示版本、构建号、源码完整提交、官方基线及其提交、镜像标签和镜像ID。存在运行时补丁或构建约束时记录内容清单及hash。
- 未提交开发快照如需构建，显式记录`dirty`和基线提交、完整差异/文件hash；不能把它伪装成干净提交。提升正式候选前提交并逐文件核对产物来源。无法对应时重新构建并分配新号。
- 不把功能名称或内容hash当作长期展示版本；这些信息放构建清单和版本详情。
- 不追溯改名历史提交、已发布版本或镜像；保留原有证据和回退标识。

## 三环境使用同一版本

开发、永久测试、生产是环境角色，不是版本号后缀。

同一已验证镜像从测试提升到生产时，展示版本、构建号、镜像ID不变；即使隔日部署也不重新编号、不重编。若需要改变源码、内置配置、版本信息或构建产物，视为新构建，分配新号并重新验证。

Web构建版本、服务端`APP_VERSION`、镜像内`VERSION`应来自同一构建定义并保持一致；仓库package.json或开发fallback不应被误当作已发布版本。版本页显示简洁版本，来源提交、上游基线与镜像ID由详情或构建清单承载。

## 上游跟踪策略

保留`upstream`远端，按需评估，不自动合并或升级。真正吸收并验证官方新版后才更新基线；暂不跟进时保留旧基线，个人构建号继续递增。是否长期跟踪上游尚未决定，不因采用此命名而视为已承诺。

如果未来决定改为独立产品版本，单独确认迁移规则；不得直接把个人功能迭代冒充官方版本更新。

## 版本比较与发布检查

`+pong...`属于SemVer构建元数据，标准SemVer比较忽略它，不能用于判断两个个人构建的新旧。需要比较个人构建时，对同一基线按日期和整数序号比较；不同官方基线按明确的上游版本规则处理。短哈希不用于排序。

不得假设BeeCount现有更新检查已支持此规则；涉及更新检测时先核对并验证比较器。

每次构建/发布前检查：

- [ ] 已确认实际官方基线和来源提交，未自动跟随最新标签。
- [ ] 已按北京时间登记唯一构建号，无失败编号复用。
- [ ] 展示版本、镜像标签及来源清单一致；开发脏快照明确标识。
- [ ] Web与API版本一致，镜像内容及ID已核验。
- [ ] 提升生产使用已验收的同一镜像，不因部署日期重编。
- [ ] 环境、备份、数据保留与Git/发布授权按项目原有规则独立执行。

## 落地状态

本规范建立时仅确立文档规则。后续候选已按该格式登记构建号、注入Web与服务端版本、核对源码和产物，并使用同一镜像完成环境提升；这不表示仓库已提供通用构建自动化或个人版本比较器。

每次新构建仍须核对实际使用的脚本、编号登记与版本注入；历史脚本中的旧标签不能作为新规范的默认入口。发布后的纯文档补充不改变已有镜像、构建号或其源码来源提交，也不能把文档新提交冒充原镜像的构建来源。
